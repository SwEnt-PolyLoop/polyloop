# PolyLoop architecture

## Layers

```
UI layer        Compose screens (15 screens, see SCREENS.md)
                  │  observe state / send user actions
ViewModel layer 15 screen ViewModels (one per screen) + DrawerViewModel (navigation drawer)
                  │  call the repositories they need (no domain layer)
Data layer      10 repositories + server clock + local upload queue (WorkManager)
                  │
Device          GPS · network status
Firebase        Auth · Firestore · Cloud Storage · Cloud Functions · FCM
External        Google Maps Platform (Maps SDK in app, Geocoding API from Functions) · Gemini API (from Functions)
```

## Repositories: one per feature

One repository per type of data, shared by every ViewModel that needs it. ViewModels and composables never read a data source (Firebase, GPS, network status) directly; they always go through a repository.

| Feature | Repository | Talks to |
| --- | --- | --- |
| Auth | AuthRepository | Firebase Auth |
| Profile | ProfileRepository | Firestore, Cloud Storage |
| Chat | ChatRepository | Firestore; Firebase Auth (the sender of a message) |
| Listing | ListingRepository | Firestore, Cloud Storage |
| Rental | RentalRepository | Firestore, Cloud Functions, Local upload queue → Cloud Storage (mid-rental photos) |
| Handover | HandoverRepository | Firestore, Cloud Storage (directly until the local upload queue exists), Cloud Functions; Firebase Auth (who takes a photo) |
| Dispute | DisputeRepository | Firestore, Cloud Storage, Cloud Functions |
| Wallet | WalletRepository | Firestore, Cloud Functions |
| Location | LocationRepository | The phone's position, through the platform location services (androidx, no extra dependency) |
| Connectivity | ConnectivityRepository | The phone's network status |

`model/RepositoryProvider` creates the repositories, so the whole app shares one instance of each. Each repository is created on first use, so Firebase is not touched until it is needed. Tests can replace a repository with a fake by assigning it before setting content, then call `reset()`. It holds the repositories implemented so far (Auth, Listing, Profile, Chat, Rental, Handover, Connectivity, Location, Wallet and Dispute); add each new repository to it when it is implemented. It also exposes the shared `FirebaseStorage` instance, for the repositories that upload photos and PDFs. Repositories that read the phone (Connectivity and Location) need the app context: `PolyLoopApplication` passes it to `RepositoryProvider.init` at startup.

`LocationRepository.currentPosition()` is a `suspend` call that returns the phone's position as a `MapPoint`, or null when the coarse location permission is not granted or there is no fix. `LocationRepositoryAndroid` uses only `ACCESS_COARSE_LOCATION` (in the manifest; the fine permission is not used) and the platform location APIs through `androidx.core`, so it adds no dependency. It asks the enabled providers in turn (fused on API 31+, then network) for one fresh fix, gives each provider 3 seconds, 6 seconds in all, then falls back to the last known location if it is at most 30 minutes old (the newest by elapsed realtime of the enabled providers, plus the passive one on API 31+), and never throws. Browse asks for the coarse location permission when it opens and it is not granted (Android stops asking after two refusals); a refusal leaves Browse working without distances. Its position is read after each load, after the permission answer and each time Browse comes back on screen, not while the user moves.

Browse distances are straight-line (great-circle) from the phone to the listing's pickup point. That point is blurred to about 1 km (see "Firestore schema"), so a distance is approximate, never an exact walking distance. `BrowseViewModel` keeps each distance in meters, and `ListingCard` shows it as "350 m" under 1 km (rounded to the nearest 10 m) and "1.2 km" from 1 km up (one decimal, the decimal separator of the current language), from the texts `distance_meters` and `distance_kilometers` in `strings.xml`. It sorts the listings by distance, and those without one (no position, or no pickup point) come last; the search is a stable sort, so equal matches keep the distance order.

`model/rental/ServerClock` gives today's date by the server's clock, for Start Pickup on Rental detail and in the chat, for Start Return on Rental detail, and for the pickup and return photos on Handover, so changing the phone's date cannot open the pickup or the return early. It is not a repository: it reads the server's time through `RentalRepository.serverNow()` (the `serverToday` Cloud Function) and takes the day in Europe/Zurich. `RepositoryProvider.serverClock` builds the app's one clock on first use, from the app context, so every screen shares one clock and one saved pair; `reset()` forgets it, and tests assign one with `InMemoryServerClockStore`. Each time the server is reached, the clock saves its time with the time since the phone booted (`SystemClock.elapsedRealtime()`, which the user cannot change) and the boot count, in SharedPreferences (`server_clock.xml`). Offline, it adds the time elapsed since then. The saved pair is dropped after a reboot, when the time since boot restarts from 0, and it is kept out of backups and device transfers (`backup_rules.xml`, `data_extraction_rules.xml`), as those values only make sense on this phone. With no pair for the current boot, the day is unknown (null): Start Pickup stays disabled on Rental detail and hidden in the chat, and Handover takes no photo; the phone's date is never used instead. Its disk and boot-count reads run on the IO dispatcher. `now()` gives the server's time itself, worked out the same way, so Handover can read the day again at the server's midnight whatever the phone's clock says.

## ViewModels: one per screen

Each screen has its own ViewModel, which holds that screen's state and calls the repositories it needs through their interfaces. ViewModels never call each other, and there is no use-case layer for now. Every ViewModel may read the signed-in user from AuthRepository and the online/offline status from ConnectivityRepository (for the offline banner and the actions disabled offline); that is not repeated below.

| Screen | ViewModel | Repositories it uses |
| --- | --- | --- |
| Sign-up / login | AuthViewModel | Auth; Profile (creates the profile on the first verified sign-in) |
| Profile & reviews | ProfileViewModel | Profile; Listing ("My listings", and someone else's published listings); Rental (where each of the own listings stands); Auth ("Sign out") |
| Edit profile | EditProfileViewModel | Profile (loads the profile, uploads the new photo, saves the name and the photo's URL) |
| Wallet | WalletViewModel | Wallet |

| Chat | ChatViewModel | Chat; Rental (link to Rental detail, the offer card and its answers); Profile (the other person); Listing (the item); `ServerClock` (today by the server's clock, for Start pickup, read only for an accepted rental, and again when the phone comes back online or the chat comes back on screen if it was unknown) |
| Browse | BrowseViewModel | Listing; Location (the phone's position, for each listing's distance) |
| Listing detail | ListingDetailViewModel | Listing (the item and its booked days); Rental (sending the request); Profile (the owner's name, photo and rating); Auth (the borrower sending the request); Wallet (the available balance the date picker compares the price to) |
| Create / edit listing | CreateListingViewModel | Listing; Rental (editing locked while a rental is accepted or active); Auth (the owner publishing the listing) |
| My rentals | MyRentalsViewModel | Rental (the item, the other person and the areas are copied on each rental, see "Firestore schema") |
| Review request | ReviewRequestViewModel | Rental (the request, sending the offer, declining, the lender's other requests whose dates overlap); Listing (the item value, shown as the suggested deposit); Profile (the borrower's rating) |

| Handover | HandoverViewModel | Handover; Rental (phase, role, deposit held); Dispute ("Flag damage"); `ServerClock` (today by the server's clock, for the pickup and return photos, read only for a rental that takes photos, again when the phone comes back online, Handover comes back on screen or the user taps "Retry", if it was unknown, and at the server's midnight while the screen stays open or, after a sleep, when it comes back on screen) |
| Dispute | DisputeViewModel | Dispute; Handover (pickup and return photos, not used yet); Rental (the item, the other person and the user's role, the deposit) |
| Admin court ruling | AdminCourtRulingViewModel | Dispute; Handover (the photos); Rental (the deposit); Listing (the item); Profile (both parties) |
| Navigation drawer (every screen) | DrawerViewModel | Profile (the signed-in user's name, photo and rating in the header); Auth (the admin claim, for Court rulings) |

If a ViewModel needs a repository that is not listed here, add it to this table in the same pull request.

DrawerViewModel is the one ViewModel not tied to a screen: the navigation drawer opens from the top bar of every screen, so `PolyLoopApp` creates it once for the whole app and refreshes it on each navigation, which follows sign-ins and sign-outs. When the signed-in user changes, it also reads whether they are an admin (`AuthRepository.isAdmin()`, see "Accounts"), and the drawer lists Court rulings only then. The read is not repeated for the same user, so an admin whose read failed (offline, for example) sees Court rulings once they sign in again or the app restarts.

## Core rule: the app expresses intent, Cloud Functions decide

The app writes only content it owns (listings, profile fields, chat messages, photos). Anything that moves money or changes who holds an item is done by Cloud Functions, called from repositories:

- rental status changes (request, accept, decline, cancel, pickup, return, close)
- deposit offers and counteroffers
- reserving and releasing the rental price and the deposit
- wallet balance changes (recharge, payments, late fees, refunds)
- dispute outcomes and applying court rulings

Firestore security rules must reject client writes to those fields.

## Rental statuses

Requested → Accepted → Active → Returned → Closed, plus Declined, Cancelled, Overdue, Lost, Disputed, Frozen.

## Product rules

**Accounts**
- Only @epfl.ch emails, checked with a regex, plus Firebase email verification. Name asked at sign-up; photo added later in Profile.
- Sign-up passwords need at least 8 characters (at most 4096, refused as too long), an uppercase letter, a lowercase letter, a number from 0 to 9 and a special character from a fixed list (see SCREENS.md); the app checks them before calling Firebase, whose password policy (enforced on the project) accepts every password that follows them. Logging in does not check them, so existing accounts keep working.
- An account must verify its email within 5 minutes of signing up, or it is deleted, so nobody can block an address by signing up with it (someone else's, or a typo). The Cloud Function `deleteExpiredSignUpsEvery5Minutes` checks every 5 minutes, so an expired account is gone 5 to 10 minutes after sign-up. Unverified accounts cannot write to Firestore or Storage, so only the Auth account is deleted.
- Admins are identified by the Firebase custom claim `admin` set to true. It is set outside the app with the Admin SDK, for example from a one-off Node script: `getAuth().setCustomUserClaims(uid, {admin: true})`, and `{admin: false}` removes it (this call replaces all of the user's custom claims). The app reads it from a fresh ID token (`getIdToken(true)`), so a change shows at the next read without signing out; nobody is an admin when nobody is signed in, offline, or when the read fails.

**Money (PolyPoints)**
- In-app currency: PolyPoints (PP), 1 CHF = 1 PP. Recharge on the Wallet screen with a whole CHF amount from 1 to 99,999 (the same cap as a listing price); a recharge that would overflow the balance is refused. Payments are simulated. No withdrawals.
- Every new user starts with 120 PP: when their profile is created, on their first verified log-in, the `createWalletOnProfile` Cloud Function creates `wallets/{uid}` with `available` 120, nothing held, and one `RECHARGE` history row of +120 PP (id `starting_balance`, no item). A wallet that already exists is left as it is, so nobody gets them twice.
- Sending a request reserves the rental price (price per day × days) from the borrower's balance; the request fails if the balance is too low. The wallet shows that price as `heldForRentals` and the deposits as `heldAsDeposits`; `reserved` is their sum, computed and never stored, and `available` + `reserved` is the user's total. A missing field reads as 0. `requestRental` holds the price in the transaction that creates the request: the borrower's `available -= totalPrice` and `heldForRentals += totalPrice`, with one `RENTAL_PAYMENT` row `-totalPrice` at the id `rental_price_held_<rentalId>` (see "Creating a request"). Requests sent before that hold nothing, so `payLender` and the pickup scan take their price from `available` (see `payLender`). Nothing gives a held price back yet: a decline will (#495), and so will a cancel (#429).
- The lender is paid the rental price when the pickup scan is confirmed (`confirmHandover`), from the price held at request: the borrower's `heldForRentals -= price` and the lender's `available += price`. The borrower's history gets no row then, as their `available` went down when the price was held; the lender's gets `+price`. `payLender` does the same payment on its own, to make up a payment that was missed.
- The deposit is negotiated before acceptance, and only the deposit: the rental price is fixed. The item value is shown as the suggested deposit. An offer or a counteroffer is a whole amount from 1 to 99,999 PP (the same cap as a listing price).
    1. On a request without an offer, the lender either sends an offer (the deposit and both exact addresses) or declines.
    2. On the lender's offer, the borrower accepts, declines or sends one counteroffer; a counteroffer the borrower's available balance cannot cover is refused.
    3. On a counteroffer, the lender accepts or declines. There is no further round.
- The rental stays `REQUESTED` during the negotiation. Accepting makes it `ACCEPTED`; the deposit is reserved then, and acceptance fails if the balance is too low. Declining an offer or a counteroffer makes it `DECLINED`.
- An offer or a counteroffer expires after 1 week without an answer, or on the rental's first day (from midnight in Zurich, like every rental date) if that comes sooner, and the rental becomes `DECLINED`. It cannot be accepted after that. A request that has no offer yet on the rental's first day becomes `DECLINED` then too, since the lender can no longer make one; `expireOffers` declines it in its hourly run, with a `SYSTEM` message in the chat. `requestRental` reserves the rental price, so every decline, this one included, must release it (#495; not done yet).
- The wallet is stored in Firestore (see "Firestore schema"). Accepting an offer (`respondToOffer`, `ACCEPT`) holds the deposit in the borrower's wallet, in the same transaction, and fails with an insufficient funds error (`failed-precondition`) if the borrower's `available` balance is too low, leaving the rental `REQUESTED`. The rental price is held since the request (see above). The pickup scan (`confirmHandover`) pays the lender, through the same steps as `payLender`. Nothing releases or splits a held deposit yet.

**Listings and booking**
- A title of at most 80 characters and a description of at most 2,000. A listing already longer, written before the limit, stays readable, but the rules refuse any edit of it until it fits.
- Price per day. The lender sets an availability window; the borrower picks dates inside it with a date picker.
- 3 to 10 listing photos, taken with the in-app camera only (no gallery).
- Pickup and drop-off addresses are typed as text; a Cloud Function geocodes them when the listing is saved. Only the area is public (its name and a point rounded to about 1 km); the exact address is shown after acceptance.
- A 1-day buffer comes before and after every booking. Booked days and buffer days are not selectable.
- Accepting a request auto-declines other requests whose dates overlap (buffer included).
- Your own listings never appear in Browse. Categories are a hardcoded list: Electronics, Sports & outdoor, Books & course material, Tools & DIY, Kitchen & home, Music, Other.

**Cancelling**
- Either party can cancel until the day before pickup. On the pickup day the rental is locked.
- A request that was never accepted can be withdrawn at any time, even on or after its pickup day.
- If the item is still not back from the previous rental on the pickup day, the rental is auto-cancelled and the borrower gets the reserved price and deposit back.

**Handover**
- QR scan at pickup and at return. The person receiving the item scans: at pickup the lender shows the code and the borrower scans; at return the borrower shows and the lender scans.
- The QR holds a secret code made for this rental and phase, so a correct scan proves the two phones met (the rental id alone would let the borrower confirm from home). The person showing it reads the code; the person scanning reads only its fingerprint (SHA-256, 64 lowercase hex characters), which checks a scan on the phone without revealing the code. A wrong code is refused on the phone and never sent. The server checks the code again before moving the rental on. The code must be at least 128 random bits from a secure generator (e.g. `crypto.randomBytes(32).toString("base64url")`): the person scanning can read the fingerprint before the meeting, and a short code (such as 6 digits) could be found by trying every code against it, then confirmed from home. Both are read with a plain `get()`, so offline the phone uses the copy Firestore kept from the last read. The fingerprint is a field of the rental, which My rentals and Rental detail already keep on the phone; the code to show is read only when Handover opens, so a phone that never opened Handover online cannot show it offline. Later, a background job (WorkManager, with the local upload queue) will read the code whenever the phone is online. Until scans can wait in the upload queue, the scan needs a connection, so the phone checks a code offline only once that queue exists.
- The code shows, and the scan is enabled, only on the pickup day and once the person has 3 photos. Until the local upload queue exists, sending a scan needs a connection.
- At each handover, each person takes their own 3 to 20 condition photos; the scan is disabled until they have 3. Photos can also be taken mid-rental from Rental detail.
- Offline: photos and QR scans go into the local upload queue and sync later. The server trusts the app's order (a scan is accepted even if its photos are still uploading).
- After the return scan, the lender chooses "Item is fine" (full deposit released) or "Flag damage" (opens a dispute).

**Late returns**
- 3-day grace period after the deadline, with reminders. Each late day costs the price per day + 2 PP, taken from the deposit and paid to the lender. Fees stop when the deposit is used up. After 3 days the item is Lost and the rest of the deposit goes to the lender.

**Disputes**
1. Direct settlement: parties propose splits in percent; accept or counter. Auto-escalates after 30 days without agreement; either party can escalate sooner. It is the only stage that escalates, by hand or on its own.
2. LLM proposal: a Cloud Function sends the item and both parties' pickup and return photos to Gemini and gets a split + reasoning. Both parties accept or reject. If it fails, either party can try again (up to 3 attempts) or reject.
3. Court: once the dispute reaches court, because either party rejected the LLM proposal, the deposit is frozen. Either party uploads the court ruling PDF; Gemini pre-fills the split; an admin reviews it on the Admin court ruling screen and applies or rejects it.
- A split is applied in whole PolyPoints: the borrower's share is rounded down and the lender gets the rest, so the shares always add up to the deposit (50% of 33 PP gives 16 PP to the borrower, 17 PP to the lender). The Cloud Functions that apply a split must round the same way as the app.
- The chat stays open during a dispute. Reviews (1–5 stars, no text for now) are prompted when a rental closes, however it closed.
- For now an agreement only settles the dispute and closes the rental, and no money is released or split: the deposit is held when an offer is accepted, but nothing releases or splits a held deposit yet, so it stays held after an agreement.
- For now no model is configured: `draftLlmProposal` marks every LLM proposal `FAILED` at once, until the Gemini client exists (#452), and nothing lets the parties accept, reject or retry it yet (#432), so an escalated dispute still has no way forward.

## Technical choices

Packages: `model/` (data and repositories), `ui/` (screens and their ViewModels), `ui/theme/` (theme). ViewModels depend on repository interfaces and never import Firebase. New Firestore repositories use the shared helpers in `model/firestore/FirestoreHelpers.kt` (reading fields, errors, write timeout, listening to a query, calling a Cloud Function) instead of copying them; Rental, Listing, Profile, Chat, Handover, Wallet and Dispute use them.

Cloud Functions live in `functions/`, a separate TypeScript project (Node 22, `firebase-functions` v2, Jest). `src/index.ts` exports every function and sets the region, `europe-west1`, next to the Firestore database (`eur3`). In `functions/`: `npm ci` installs, `npm run lint` type-checks, `firebase emulators:exec --only firestore "npm test"` runs the tests on the Firestore emulator (external APIs are faked), and `firebase deploy --only functions` deploys (needs the Blaze plan). API keys live in Secret Manager. CI runs the install, lint, build and test steps in its own job. Rental detail opens Start Pickup and Start Return, the chat Start Pickup, and Handover its pickup and return photos, from `serverToday`'s `now`, through `ServerClock` (see "Repositories: one per feature"), which works the day out offline from the last answer; the app does not use `today` yet.

**`reserveDeposit({rentalId})`** holds the deposit of an accepted rental. Accepting an offer already holds it (see below), so this is a safe repeat: it finds the row and succeeds without a second charge. The caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower or its lender, and the rental must be `ACCEPTED`, unless the deposit is already held. The checks run in this order: the rental exists, the caller is a participant, the borrower is valid, the row already exists (the call succeeds, even if the rental has moved on, e.g. to `ACTIVE`), the status is `ACCEPTED`, the deposit is valid, the balance covers it. The amount (`deposit`), the people (`borrowerId`, `ownerId`) and the item title (`listingTitle`) come from the rental, never from the request. In one Firestore transaction on the borrower's wallet, `available -= deposit`, `heldAsDeposits += deposit`, and one `DEPOSIT_HELD` row is added to the borrower's history with the id `deposit_held_<rentalId>`, the amount `-deposit`, the item title and a server timestamp. If `available` is below the deposit, the call fails with an insufficient funds error (`failed-precondition`) and writes nothing. It is idempotent: the row is looked for in the same transaction, so a second call for the same rental changes nothing and succeeds. It writes only the borrower's wallet, even when the lender calls it, and returns nothing, so the lender learns only whether the borrower's balance covers the deposit (the insufficient funds error), never the balance itself. The read and write steps on a wallet are in `functions/src/wallet.ts`, for the other functions that move PolyPoints: `readWallet`, `requireFunds` (the funds check, called after the other checks) and `writeDepositHold`. `respondToOffer` with `ACCEPT` uses the same steps inside its own transaction: the borrower's wallet is read with the other reads, and the check, run before any write, throws the same insufficient funds error with nothing written (the rental stays `REQUESTED`, the offer stays, `bookedRanges` is untouched and no overlapping request is declined). The borrower pays whoever accepts, and the amount is the offer's: after a counteroffer, the counter amount. It holds only the deposit, `DEPOSIT_HELD` row `deposit_held_<rentalId>` included; it does not reserve the rental price, call `payLender`, or release or split the deposit.

**`payLender({rentalId})`** pays the lender the rental price once the item has been picked up. The caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower or its lender, and the rental must have been picked up (status `ACTIVE` or any later one: `RETURNED`, `OVERDUE`, `DISPUTED`, `FROZEN`, `LOST`, `CLOSED`), unless the payment was already made; a payment missed while the rental was `ACTIVE` (app killed, offline scans synced together) can still be made up afterwards. The checks run in this order: the rental exists, the caller is a participant, the borrower and the lender are valid and different, the payment already exists (the call succeeds, whatever the status is by now), the status is one of those above, the price is valid, the borrower's balance covers it. The amount (`totalPrice`), the people (`borrowerId`, `ownerId`) and the item title (`listingTitle`) come from the rental, never from the request. In one Firestore transaction, the borrower's `heldForRentals -= totalPrice` (the price held when the request was sent) and the lender's `available += totalPrice` (their wallet is created if missing), and one `RENTAL_PAYMENT` row with the id `rental_payment_<rentalId>`, `+totalPrice`, the item title and a server timestamp, is added to the lender's history. The borrower's history gets no row: their `available` does not change. Whether the price is held is read from the rental's own row, `rental_price_held_<rentalId>` in the borrower's history, never from `heldForRentals`, which also holds the prices of other requests. A rental sent before requests held their price has no such row: its price is taken from the borrower's `available` instead, as before, with a `RENTAL_PAYMENT` row `-totalPrice` in the borrower's history too, and if `available` does not cover it the call fails with an insufficient funds error (`failed-precondition`) and writes nothing. A held price that `heldForRentals` no longer covers means the stored data is broken: the call fails with `internal` and writes nothing. It is idempotent: the lender's row is looked for in the same transaction, so a second call changes nothing and succeeds (payments made before this rule also wrote a row for the borrower, and still count). It returns nothing, so the lender learns only whether the price is covered, never the borrower's balances. The pickup scan uses the same steps (`functions/src/payLender.ts`: `requireParties`, `isLenderPaid`, `readLenderPayment`, `writeLenderPayment`) inside its own transaction.

**`confirmHandover({rentalId, phase, code})`** confirms a handover scanned in the app; `phase` is `PICKUP` only for now (the return scan comes with the return, and `RETURN` is refused as `invalid-argument`). The caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower, the person receiving the item. `code` is the text read from the lender's QR code, compared exactly, untrimmed, in constant time. The checks run in this order: the rental exists (`not-found`), the caller is its borrower (`permission-denied`), then, if the rental was already picked up (`ACTIVE` or any later status), the call succeeds and changes nothing, so a scan sent twice is harmless; otherwise the rental must be `ACCEPTED` (else `failed-precondition` with `details.reason` `RENTAL_CHANGED`), today in Zurich (the server's clock) must be its `startDate` (else `failed-precondition` with no reason), the code must be the one in `handoverCodes/PICKUP` (else `failed-precondition` with `details.reason` `WRONG_CODE`), and the borrower's balance must cover the price (as for `payLender`). In one transaction, the rental becomes `ACTIVE` with `pickedUpAt`, the lender is paid as by `payLender` (not again if they already were), a `SYSTEM` message "Picked up · rental started" is added, seen by the borrower, and the pickup code and `pickupCodeHash` are deleted. The photos are not checked: the server trusts the app's order. The code is made when the offer is accepted (`respondToOffer`, `ACCEPT`, in the same transaction): 32 random bytes from Node's `randomBytes`, as base64url (43 characters), stored in `rentals/{rentalId}/handoverCodes/PICKUP` (`code`), with its SHA-256 in lowercase hex as `pickupCodeHash` on the rental (`functions/src/handoverCode.ts`). Only the PICKUP code is made for now.

## Firestore schema

Dates without a time are stored as `YYYY-MM-DD` strings, prices as whole PolyPoints. Date-times (`createdAt`, `lastMessageAt`, `lastReadAt`, `sentAt`, `takenAt`) are Firestore Timestamps, set with `FieldValue.serverTimestamp()`; reads use `ServerTimestampBehavior.ESTIMATE`, because until the server confirms a write a listener otherwise sees these fields as null. When a new field is added to an existing collection, reading must give it a default value: documents written before it do not have it.

| Path | Fields | Notes |

Listings:
- `pickupArea` and `dropOffArea` are area names (e.g. "Ecublens"); `pickupPoint` and `dropOffPoint` are GeoPoints. The app creates a listing with empty names and no points; the `geocodeListingAddresses` Cloud Function fills them in. Each time `listings/{listingId}/private/addresses` is written, it geocodes each changed address (in Switzerland only) and stores its area name and its point rounded to a 0.01° grid (about 1.1 × 0.8 km around EPFL). The exact address and point never reach the public listing. A lookup that fails (e.g. the Geocoding API is down or takes more than 10 seconds) is retried for up to a day, and a result is written only if its address has not changed since, so the newest edit wins even if its run finishes first.
- Until an address is geocoded, or when it is blank, not found or its geocoding fails, its name and point are missing, and screens show a placeholder.

Rentals:
- The listing title, both names and the public areas are copied when the rental is created, so My rentals and the chat list need no other read. A missing owner name is stored as `""`; screens show a translated placeholder.
- `participants` is `[ownerId, borrowerId]`; the chat list queries it with `array-contains` only and sorts by `lastMessageAt` in the app, so it needs no composite index.
- My rentals queries `borrowerId` or `ownerId` only and sorts newest first in the app (a user has few rentals), so it needs no index.
- `lastMessageAt` is set to the same server timestamp as `createdAt` when the rental is created: the chat list sorts by it, and leaves out a rental that lacks it.
- `lastReadAt` maps each participant's uid to when they last saw the chat; it is missing until someone does, and reads as empty. The app saves the user's own entry at the server time while the chat is on screen: when it shows its messages, and each time a newer one from someone else arrives. It saves nothing while the chat is hidden (another screen on top, or the app in the background), while it shows no message, or offline, where the server time would only be set on reconnecting and would also cover messages received meanwhile; it saves once the connection is back. Sending a message saves the sender's entry in the same write, and each Cloud Function that adds a `SYSTEM` message saves the entry of the participant whose action it reports (nobody's for a scheduled job such as `expireOffers`), so a user's own messages and actions are never unread. A conversation is unread for a user when it has a last message newer than their entry, or they have no entry; the chat list then shows a red dot. Rentals created before `lastReadAt` existed show a dot on every conversation with a message until it is opened.
- `pickupAddress` and `returnAddress` stay empty until the rental is accepted; the borrower cannot read the exact addresses before that. The lender's offer stores them in `private/addresses`, and acceptance copies them onto the rental.
- `deposit` is the accepted amount in PolyPoints; missing reads as 0.
- `pickedUpAt` is when the pickup scan was confirmed, a server Timestamp set by `confirmHandover`; it is missing until then.
- `cancelledAt` is when the rental was cancelled, a server Timestamp. Nothing writes it yet (#503); once something does, only Cloud Functions will (`cancelRental`, #429, and later the auto-cancel). Missing reads as null, and Rental detail then shows "Cancelled" with no date.
- `lateFees` is the total of the late fees taken from the deposit, in PolyPoints. Only Cloud Functions will write it, the scheduled job that charges late fees, once a return is late, so a rental that was never late has no such field, and missing reads as 0.
- `offer` is the offer waiting for an answer: `amount`, `authorId`, `isCounter`, `createdAt`, `expiresAt`, and on a counteroffer `previousAmount`, the lender's offer. It is missing when no offer is waiting, and removed when the negotiation ends. `expireOffers` queries `offer.expiresAt` alone, and requests with no offer on `status` alone with the dates checked in the code, so it needs no composite index, and answering also refuses an expired offer, in case `expireOffers` has not run yet.
- `pickupCodeHash` and `returnCodeHash` are the fingerprints of the handover codes (see "Handover"): the SHA-256 of the code, as 64 lowercase hex characters. The code must be at least 128 random bits, or it could be found from its fingerprint. Written by Cloud Functions only. Missing reads as no code, and the scan stays disabled.
- Each step of the negotiation adds a `SYSTEM` message to the chat, written by the Cloud Functions; the chat's offer card reads `offer`, so there is no new message type.
- **Creating a request.** Only the `requestRental` Cloud Function creates a rental; the security rules refuse every client creation. The app sends the listing's id and the days only. The caller must be signed in with a verified `@epfl.ch` account and must not own the listing; the listing must exist and be `PUBLISHED`; the days must be inside its availability window, the first one after today in Europe/Zurich (a request starting today could get no offer), and must not conflict with `bookedRanges`, buffer day included; all these refusals carry `details.reason` `DATES_UNAVAILABLE`. Sending the same request again (same borrower, listing and days, still `REQUESTED`) returns the first rental, so a retry after a lost answer never creates a second one; a pending request of the same borrower with other days in common is refused with `already-exists`. The listing is read and the rental written in one transaction, so two requests sent at once are checked against the same `bookedRanges` (both go through, since a pending request blocks no day). Every other field comes from the server: the owner and the borrower names from `users/`, the title, the first photo (`""` without one), the price per day and the areas from the listing, `totalPrice` (price per day × days), `participants`, status `REQUESTED`, empty addresses and last message, and `createdAt` and `lastMessageAt` at the same server timestamp. A booked day fails with `failed-precondition` and `details.reason` `DATES_UNAVAILABLE`, a missing listing with `not-found` and an unpublished one with `failed-precondition`; the app reads them to show "These dates are no longer available" or the listing as not found. The same transaction holds the rental price in the borrower's wallet (see "Money"); a borrower whose `available` balance is below `totalPrice` is refused with `failed-precondition` and `details.reason` `INSUFFICIENT_FUNDS`, checked after every other refusal, and nothing is written. A request sent again returns the first rental without holding the price a second time, even once the balance is spent. Two requests of one borrower sent at once read the same wallet, so Firestore retries one of them on the new balance: each holds its own price, or the second is refused. Afterwards the participants can change only `lastMessage` (never empty, which would read as no message), `lastMessageAt` (to the server time) and their own entry of `lastReadAt` (to the server time), and an update must change something.

Wallet:
- `WalletRepositoryFirestore` only reads, with snapshot listeners that serve the cache first (and `MetadataChanges.INCLUDE`), so the wallet and the history stay readable offline from the cache, and it never forces a server read. A missing wallet document, or an empty history, that comes from the cache is not emitted: from an empty cache (after a reinstall, or a first launch offline) it cannot be told from a real empty one, so it is emitted only once the server has confirmed it, and until then the balance and the history are unknown (not 0, not empty). The history is not sorted there (`WalletViewModel` sorts it). An invalid uid reads as an empty wallet and history. `recharge` always fails ("not available yet") until a recharge Cloud Function exists.
- Until recharging exists, a user has only the 120 PP they start with (see "Money"); give a test user more by hand: edit `wallets/{uid}` in the Firebase console, or write it with a script against the emulator (Admin SDK or the emulator's REST API with the `Bearer owner` token, which skips the rules). Add a matching `RECHARGE` row in `transactions` if the history should add up to `available`.

Disputes:
- One per rental, at the rental's id. Nothing is copied from the rental: the item, both participants and the deposit are read from it.
- `stage` is `SETTLE`, `LLM_PROPOSAL` or `COURT`. `proposals` lists every split, oldest first, each `{authorId, lenderPercent, createdAt}` with `lenderPercent` a whole number from 0 to 100; `createdAt` is set by the Cloud Function from its own clock, because a server timestamp is not allowed inside a list. `escalatesAt` is when direct settlement escalates by itself: 30 days after the dispute opens, to be set by the Cloud Function that will open it (not written yet), and not changed afterwards. A dispute without it never escalates by itself, in the Cloud Functions and in the app, which then shows no days left. `escalatedBy` is the uid of the participant who escalated, or null when it escalated by itself or has not escalated. `agreedAt` is set when a split is accepted, and null before; it, not `stage`, tells whether the dispute is settled (an agreement leaves `stage` at `SETTLE`).
- `proposeSplit({rentalId, lenderPercent})` adds a split, refused if it is the latest one or if the dispute already holds 500 (far more than a real negotiation; it keeps a script or a bug from growing the document towards Firestore's 1 MiB limit). `acceptSplit({rentalId, lenderPercent})` accepts the latest split, which must be the other participant's and give the lender `lenderPercent`; it sets `agreedAt` and closes the rental. `escalateDispute({rentalId})` moves the dispute to `LLM_PROPOSAL`. The hourly `escalateDisputes` does the same, with `escalatedBy` null, for each dispute still in `SETTLE` and not settled once `escalatesAt` has passed; it queries `escalatesAt` alone, so it needs no composite index. Like the callables, it leaves a dispute whose rental is missing or not `DISPUTED` as it is, and logs it as a failure at each run. The three callables refuse a settled dispute, one no longer in `SETTLE`, and one whose rental is not `DISPUTED` (only the Function that opens a dispute sets that status, so an agreement never overwrites another one). Once `escalatesAt` has passed, even before the sweep runs, they escalate the dispute instead, as the sweep would (`escalatedBy` null), and fail with `STAGE_CHANGED`. A request that lost a race fails with `failed-precondition` and `details.reason`: `PROPOSAL_CHANGED` (the latest split is not the one accepted) or `STAGE_CHANGED` (the dispute was settled or left `SETTLE`); the app reads the reason, never the message.
- `llmProposal` is the LLM proposal: `{status, attempt, lenderPercent, reasoning, model, photoIds, createdAt}`. Escalating, by hand or by itself, creates it as `{status: PENDING, attempt: 1}` in the same write; it is missing in `SETTLE` and on disputes escalated before it existed. `status` is `PENDING` (waiting for the model), `READY` or `FAILED`. `lenderPercent` (a whole number from 0 to 100), `reasoning` (English, at most 2,000 characters), `model` (the model's name) and `photoIds` (the condition photos it was sent) are set only when `READY`; `createdAt` is the server time it became `READY` or `FAILED`.
- The trigger `draftLlmProposal` runs on each update of `disputes/{rentalId}` and acts only when the update starts a new `attempt` of a `PENDING` proposal, so its own writes never start it again. Through the `SplitAdvisor` interface (`functions/src/splitAdvisor.ts`, see docs/adr/0001), it sends the model the item's title, description and value, the deposit, the rental's dates, and both parties' pickup and return photos (at most 20 per party per phase, oldest first, given by their Storage path, never their `url`), naming the missing ones; never the split proposals nor the chat (docs/adr/0002). The rule it gives the model: the lender's share is the cost of new damage as a percentage of the deposit, normal wear is not damage, and missing return evidence counts against the borrower. It writes `READY`, or `FAILED` when no model is configured, the model refuses for good or its answer breaks these rules; a failure that may pass (the model is down or slow) is retried for up to a day, then `FAILED`. The result is written only if the dispute is still in `LLM_PROPOSAL`, not settled, `PENDING` on the same attempt and its rental `DISPUTED`, so overlapping runs keep the first answer. Each result adds a `SYSTEM` message to the chat, from nobody.
- An agreement and an escalation add a `SYSTEM` message to the rental's chat; a proposal adds none.

Listing photos uploaded by the app go to Cloud Storage under `listings/{listingId}/`, as `0.jpg` to `9.jpg`, each tagged with the uid of the user who uploaded it (custom metadata `uploader`), so the Storage rules can check the owner and the uploader. Photos added before this rule live in `listing_images/` and keep working through their download URLs. Condition photos go to `rentals/{rentalId}/photos/{photoId}.jpg`, named after their Firestore document, so `{uid}_PICKUP_{n}.jpg` (see the schema above); photos stored before the slot ids keep their random names. A profile photo goes to `users/{uid}/profile.jpg`, one file per user that each new photo replaces; replacing it gives a new download URL, so the new photo is not hidden by an image cache.

## Security rules

`firestore.rules` and `storage.rules` are listed in `firebase.json`, so the emulators enforce them; `FirestoreRulesTest` and `StorageRulesTest` (in `androidTest/.../rules/`) check them. Every read and write needs a verified `@epfl.ch` account. Beyond the notes in the schema above:
- A listing must pass the same checks as `Listing.canPublish` (a title of at most 80 characters and a description of at most 2,000, neither blank, 3 to 10 photo URLs, all strings, prices from 1 to 99,999 PP, `availableFrom` before `availableTo`, a known category and status). Clients never write `bookedRanges` (a Cloud Function will, on acceptance) and never change `ownerId`. They create `pickupArea` and `dropOffArea` empty, never write `pickupPoint` or `dropOffPoint`, and never change any of the four afterwards (`geocodeListingAddresses` does). A listing cannot be created at an id whose `private/addresses` is left over from a deleted listing.
- A rental request must match its listing, which must be `PUBLISHED`: same owner, title, first photo (`""` if the listing has none), price per day and areas, dates inside the availability window, and `totalPrice` equal to the price per day × the number of days.
- Clients never write a rental's `deposit`, `offer`, `pickupAddress` or `returnAddress`, and have no access to `rentals/{rentalId}/private/addresses`.
- Wallets: a user reads only their own `wallets/{uid}` and its `transactions`; nobody writes them from the app, the owner included (`allow write: if false`). Cloud Functions write them.
- A dispute is read only by the two participants of its rental (`participants`), and never written by a client.
- A handover code (`rentals/{rentalId}/handoverCodes/{phase}`) is read only by the person who shows it: the lender for `PICKUP`, the borrower for `RETURN`; any other phase by nobody. No client writes it, nor the fingerprints on the rental (`pickupCodeHash`, `returnCodeHash`), which the rental's update rule already keeps out of reach.
- Profiles: a user creates and edits only their own, with their own email; `averageRating` and `reviewCount` are left to Cloud Functions.
- Storage: listing photos must be images under 10 MB (the in-app camera takes about 1440 × 1080 JPEGs at quality 80), named `0.jpg` to `9.jpg` and tagged with the uid of the user writing them. They are uploaded before the listing document exists, so a folder whose listing does not exist yet is open to any verified user; once it exists, only the owner may change it. A photo can be replaced or deleted only by the user who uploaded it, even once its listing is deleted; photos uploaded before the tag existed have none, so only an admin can change or delete them. These rules read Firestore, so the first deploy asks to let Storage read Firestore.
- Storage: a profile photo can be read by any verified user and changed or deleted only by its user; it must be an image under 5 MB, and no other file is allowed under `users/`. The in-app camera takes photos at 1440 × 1080 with JPEG quality 80, a few hundred KB, well under this limit.
- Storage: condition photos are read and added only by the rental's two participants, pickup photos while the rental is Accepted and return photos while it is Active or Overdue, as images under 10 MB; they are never replaced or deleted. The file name must be the signed-in user's own slot of that phase, `{uid}_{phase}_{0..19}.jpg`, so a person adds at most 20 per phase: a slot is written once because nobody replaces a photo.
- Condition photo cap (#428): Firestore rules cannot count documents, so the cap is part of the id. A condition photo's id must be the user's own slot of its phase, `{uid}_{phase}_{0..19}` (Firestore) and the file `{uid}_{phase}_{0..19}.jpg` (Storage), on top of the checks above. Photos with other ids, such as the random ones stored before slot ids or sent by old app versions, are refused when added and are not counted. The rules refuse the random ids that old app versions send, so deploy them only after the app update is out. A slot whose file exists in Storage without a document (an upload that finished but whose document was never written) is skipped for the rest of the session: `addPhoto` sets it aside and tries the next slot.
- Profile photo URL (#428): a profile's `photoUrl` must be `""` or the download URL of the user's own `users/{uid}/profile.jpg` in this project's bucket (`https://firebasestorage.googleapis.com/v0/b/<bucket>/o/users%2F<uid>%2Fprofile.jpg?alt=media&token=<token>`). It is checked when the profile is created, and when it is updated only if `photoUrl` changes, so an old stored value does not block a name change. The bucket name is written in `firestore.rules`, since the rules cannot read it. The same URL on the Storage emulator's hosts (`http://10.0.2.2:9199`, `http://localhost:9199`, `http://127.0.0.1:9199`, any one-segment bucket) is also accepted, so that the emulator tests can use the URL of a real upload; it is accepted in production too.
- Not enforced yet: the pickup and return days of condition photos (checked in the app); a condition photo's `url` pointing at its own file in Storage (the rules only require a string, so a modified client could point it at any image); locking a listing's edit and delete while a rental of it is accepted or active; photo URLs pointing at this listing's Storage folder; new photos in folders with no listing (any verified user can still add up to 10 under a made-up or deleted id); a limit on how many requests one borrower sends for a listing (`requestRental` only refuses a second pending request of the same borrower with days in common); keeping drafts private: any verified user can read every listing, so someone else's profile downloads and caches their drafts and only leaves them out on the phone (#308).
