# PolyLoop architecture

## Layers

```
UI layer        Compose screens (15 screens, see SCREENS.md)
                  │  observe state / send user actions
ViewModel layer 15 screen ViewModels (one per screen) + DrawerViewModel (navigation drawer)
                  │  call the repositories they need (no domain layer)
Data layer      10 repositories + server clock + local upload queue (WorkManager)
                  │
Device          GPS · network status
Firebase        Auth · Firestore · Cloud Storage · Cloud Functions · FCM
External        Google Maps Platform (Maps SDK in app, Geocoding API from Functions) · Gemini API (from Functions)
```

## Repositories: one per feature

One repository per type of data, shared by every ViewModel that needs it. ViewModels and composables never read a data source (Firebase, GPS, network status) directly; they always go through a repository.

| Feature | Repository | Talks to |
| --- | --- | --- |
| Auth | AuthRepository | Firebase Auth |
| Profile | ProfileRepository | Firestore, Cloud Storage |
| Chat | ChatRepository | Firestore; Firebase Auth (the sender of a message) |
| Listing | ListingRepository | Firestore, Cloud Storage |
| Rental | RentalRepository | Firestore, Cloud Functions, Local upload queue → Cloud Storage (mid-rental photos) |
| Handover | HandoverRepository | Firestore, Local upload queue → Cloud Storage and Firestore (condition photos), Cloud Functions; Firebase Auth (who takes a photo) |
| Dispute | DisputeRepository | Firestore, Cloud Storage, Cloud Functions |
| Wallet | WalletRepository | Firestore, Cloud Functions |
| Location | LocationRepository | The phone's position, through the platform location services (androidx, no extra dependency) |
| Connectivity | ConnectivityRepository | The phone's network status |

`model/RepositoryProvider` creates the repositories, so the whole app shares one instance of each. Each repository is created on first use, so Firebase is not touched until it is needed. Tests can replace a repository with a fake by assigning it before setting content, then call `reset()`. It holds the repositories implemented so far (Auth, Listing, Profile, Chat, Rental, Handover, Connectivity, Location, Wallet and Dispute); add each new repository to it when it is implemented. It also exposes the shared `FirebaseStorage` instance, for the repositories that upload photos and PDFs. Repositories that read the phone (Connectivity and Location) need the app context: `PolyLoopApplication` passes it to `RepositoryProvider.init` at startup.

`LocationRepository.currentPosition()` is a `suspend` call that returns the phone's position as a `MapPoint`, or null when the coarse location permission is not granted or there is no fix. `LocationRepositoryAndroid` uses only `ACCESS_COARSE_LOCATION` (in the manifest; the fine permission is not used) and the platform location APIs through `androidx.core`, so it adds no dependency. It asks the enabled providers in turn (fused on API 31+, then network) for one fresh fix, gives each provider 3 seconds, 6 seconds in all, then falls back to the last known location if it is at most 30 minutes old (the newest by elapsed realtime of the enabled providers, plus the passive one on API 31+), and never throws. Browse asks for the coarse location permission when it opens and it is not granted (Android stops asking after two refusals); a refusal leaves Browse working without distances. Its position is read after each load, after the permission answer and each time Browse comes back on screen, not while the user moves.

Browse distances are straight-line (great-circle) from the phone to the listing's pickup point. That point is blurred to about 1 km (see "Firestore schema"), so a distance is approximate, never an exact walking distance. `BrowseViewModel` keeps each distance in meters, and `ListingCard` shows it as "350 m" under 1 km (rounded to the nearest 10 m) and "1.2 km" from 1 km up (one decimal, the decimal separator of the current language), from the texts `distance_meters` and `distance_kilometers` in `strings.xml`. It sorts the listings by distance, and those without one (no position, or no pickup point) come last; the search is a stable sort, so equal matches keep the distance order.

The local upload queue (`model/handover/HandoverUploadQueue`, #511) sends condition photos once the phone is online, even after the app was closed or the phone restarted, with WorkManager. It is not a repository: `HandoverRepositoryFirestore` uses it, and `RepositoryProvider.handoverUploadQueue` builds the app's one queue on first use. `addPhoto` picks the photo's slot (the lowest one neither sent nor queued) and takes the time it was taken from Handover (`ServerClock.savedNow()`, worked out from the pair saved when Handover read the day, so a photo never waits for the server), then the queue copies the file to its own folder (`files/handover_upload_queue/`, which the camera's cleanup never touches) and adds one WorkManager job for it, which runs only with a network. Each photo is its own job: in a chain, one failed job would fail every job after it, and no order is needed, since each photo carries its `takenAt`. The job (`HandoverPhotoWorker`) uploads the file, tagged with its `takenAt`, unless a file with that tag is already in Storage (another file at the slot, e.g. a refused photo's, is never reused: the rules refuse to replace it, so the photo ends refused), then writes the document unless it already exists, so running it again is safe; it deletes the copy once the photo is sent, retries later when the connection fails, and gives up when the server refuses the photo (e.g. more than a day late), marking it refused. What waits is read from WorkManager itself, through tags on the jobs, with no other storage: `observeMyPhotos` lists the photos still waiting (their url is the copy on the phone) with the sent ones, and leaves out refused ones. Photos taken mid-rental and QR scans (#514) do not use it yet.

`model/rental/ServerClock` gives today's date by the server's clock, for Start Pickup on Rental detail and in the chat, for Start Return on Rental detail, and for the pickup and return photos on Handover, so changing the phone's date cannot open the pickup or the return early. It is not a repository: it reads the server's time through `RentalRepository.serverNow()` (the `serverToday` Cloud Function) and takes the day in Europe/Zurich. `RepositoryProvider.serverClock` builds the app's one clock on first use, from the app context, so every screen shares one clock and one saved pair; `reset()` forgets it, and tests assign one with `InMemoryServerClockStore`. Each time the server is reached, the clock saves its time with the time since the phone booted (`SystemClock.elapsedRealtime()`, which the user cannot change) and the boot count, in SharedPreferences (`server_clock.xml`). Offline, it adds the time elapsed since then. The saved pair is dropped after a reboot, when the time since boot restarts from 0, and it is kept out of backups and device transfers (`backup_rules.xml`, `data_extraction_rules.xml`), as those values only make sense on this phone. With no pair for the current boot, the day is unknown (null): Start Pickup stays disabled on Rental detail and hidden in the chat, and Handover takes no photo; the phone's date is never used instead. Its disk and boot-count reads run on the IO dispatcher. `now()` gives the server's time itself, worked out the same way, so Handover can read the day again at the server's midnight whatever the phone's clock says.

In the composables, everything that depends on the phone's date (greyed-out past days in the date pickers, a year shown only when it is not this year, a chat message's time shown only for today's messages) reads `LocalToday` (`ui/components/LocalToday.kt`), a CompositionLocal holding today's date that `PolyLoopApp` provides once with `ProvideToday`, so a screen left open across midnight does not keep yesterday's date. A `TodayTracker` reads the date from the phone's clock and time zone when the app opens, again each time it comes back to the foreground, as either may have changed meanwhile, and at each local midnight while it stays there. Nothing listens for a change of the clock or time zone made while the app stays in the foreground (an automatic time zone change when crossing a border, a large network time correction): it is read at the midnight being waited for, up to a day later. Composables never call `LocalDate.now()`: a screen's content takes `today` as a parameter defaulting to `LocalToday.current`, so tests and previews can pass a fixed date, and passes it down to the parts that show dates. Without a provider, `LocalToday` is the phone's date the first time it is read in the process, as Compose computes a default only once, so anything that shows dates must be under `ProvideToday`; the default is for tests and previews only. ViewModels read the phone's clock through a function they take instead, called when they need it: `ListingDetailViewModel`'s `today`, and the `clock` of the Chat, My rentals and Rental detail ViewModels (whether an offer has expired) and of `DisputeViewModel` (the days left before a dispute escalates).

## ViewModels: one per screen

Each screen has its own ViewModel, which holds that screen's state and calls the repositories it needs through their interfaces. ViewModels never call each other, and there is no use-case layer for now. Every ViewModel may read the signed-in user from AuthRepository and the online/offline status from ConnectivityRepository (for the offline banner and the actions disabled offline); that is not repeated below.

| Screen | ViewModel | Repositories it uses |
| --- | --- | --- |
| Sign-up / login | AuthViewModel | Auth; Profile (creates the profile on the first verified sign-in) |
| Profile & reviews | ProfileViewModel | Profile; Listing ("My listings", and someone else's published listings); Rental (where each of the own listings stands); Auth ("Sign out") |
| Edit profile | EditProfileViewModel | Profile (loads the profile, uploads the new photo, saves the name and the photo's URL) |
| Wallet | WalletViewModel | Wallet |

| Chat | ChatViewModel | Chat; Rental (link to Rental detail, the offer card and its answers); Profile (the other person); Listing (the item); `ServerClock` (today by the server's clock, for Start pickup, read only for an accepted rental, and again when the phone comes back online or the chat comes back on screen if it was unknown) |
| Browse | BrowseViewModel | Listing; Location (the phone's position, for each listing's distance) |
| Listing detail | ListingDetailViewModel | Listing (the item and its booked days); Rental (sending the request); Profile (the owner's name, photo and rating); Auth (the borrower sending the request); Wallet (the available balance the date picker compares the price to) |
| Create / edit listing | CreateListingViewModel | Listing; Rental (editing locked while a rental is accepted or active); Auth (the owner publishing the listing) |
| My rentals | MyRentalsViewModel | Rental (the item, the other person and the areas are copied on each rental, see "Firestore schema") |

| Handover | HandoverViewModel | Handover; Rental (phase, role, deposit held); Dispute ("Flag damage"); `ServerClock` (today by the server's clock, for the pickup and return photos, read only for a rental that takes photos, again when the phone comes back online, Handover comes back on screen or the user taps "Retry", if it was unknown, and at the server's midnight while the screen stays open or, after a sleep, when it comes back on screen) |
| Dispute | DisputeViewModel | Dispute; Handover (pickup and return photos, not used yet); Rental (the item, the other person and the user's role, the deposit) |

If a ViewModel needs a repository that is not listed here, add it to this table in the same pull request.

DrawerViewModel is the one ViewModel not tied to a screen: the navigation drawer opens from the top bar of every screen, so `PolyLoopApp` creates it once for the whole app and refreshes it on each navigation, which follows sign-ins and sign-outs. When the signed-in user changes, it also reads whether they are an admin (`AuthRepository.isAdmin()`, see "Accounts"), and the drawer lists Court rulings only then. The read is not repeated for the same user, so an admin whose read failed (offline, for example) sees Court rulings once they sign in again or the app restarts.

## Core rule: the app expresses intent, Cloud Functions decide

The app writes only content it owns (listings, profile fields, chat messages, photos). Anything that moves money or changes who holds an item is done by Cloud Functions, called from repositories:

- rental status changes (request, accept, decline, cancel, pickup, return, close)
- deposit offers and counteroffers
- reserving and releasing the rental price and the deposit
- wallet balance changes (recharge, payments, late fees, refunds)
- dispute outcomes and applying court rulings

Firestore security rules must reject client writes to those fields.

## Rental statuses

Requested → Accepted → Active → Returned → Closed, plus Declined, Cancelled, Overdue, Lost, Disputed, Frozen. A returned rental whose lender flags damage becomes Disputed (`openDispute`).

## Product rules

**Accounts**
- Only @epfl.ch emails, checked with a regex, plus Firebase email verification. Name asked at sign-up; photo added later in Profile.
- Sign-up passwords need at least 8 characters (at most 4096, refused as too long), an uppercase letter, a lowercase letter, a number from 0 to 9 and a special character from a fixed list (see SCREENS.md); the app checks them before calling Firebase, whose password policy (enforced on the project) accepts every password that follows them. Logging in does not check them, so existing accounts keep working.
- A forgotten password is reset through Firebase: `AuthRepository.sendPasswordResetEmail` sends the email, and the user sets the new password on Firebase's page, where the project's password policy applies but the app's sign-up rules do not; logging in does not check them, so the new password works either way. It succeeds for an address without an account too: Firebase sends nothing then, and says so only when email enumeration protection is off (`FirebaseAuthInvalidUserException`), which the app treats as a sent email, so it never tells who has an account.
- An account must verify its email within 5 minutes of signing up, or it is deleted, so nobody can block an address by signing up with it (someone else's, or a typo). The Cloud Function `deleteExpiredSignUpsEvery5Minutes` checks every 5 minutes, so an expired account is gone 5 to 10 minutes after sign-up. Unverified accounts cannot write to Firestore or Storage, so only the Auth account is deleted.
- Admins are identified by the Firebase custom claim `admin` set to true. It is set outside the app with the Admin SDK, for example from a one-off Node script: `getAuth().setCustomUserClaims(uid, {admin: true})`, and `{admin: false}` removes it (this call replaces all of the user's custom claims). The app reads it from a fresh ID token (`getIdToken(true)`), so a change shows at the next read without signing out; nobody is an admin when nobody is signed in, offline, or when the read fails.

**Money (PolyPoints)**
- In-app currency: PolyPoints (PP), 1 CHF = 1 PP. Recharge on the Wallet screen with a whole CHF amount from 1 to 99,999 (the same cap as a listing price); a recharge that would overflow the balance is refused. Payments are simulated. No withdrawals.
- Every new user starts with 120 PP: when their profile is created, on their first verified log-in, the `createWalletOnProfile` Cloud Function creates `wallets/{uid}` with `available` 120, nothing held, and one `RECHARGE` history row of +120 PP (id `starting_balance`, no item). A wallet that already exists is left as it is, so nobody gets them twice.
- Sending a request reserves the rental price (price per day × days) from the borrower's balance; the request fails if the balance is too low. The wallet shows that price as `heldForRentals` and the deposits as `heldAsDeposits`; `reserved` is their sum, computed and never stored, and `available` + `reserved` is the user's total. A missing field reads as 0. (Not yet (#357): nothing reserves the price yet, so until then `payLender` and the pickup scan take a price that is not held from `available`, see `payLender`.)
- The lender is paid the rental price when the pickup scan is confirmed (`confirmHandover`), from the price held at request: the borrower's `heldForRentals -= price` and the lender's `available += price`. The borrower's history gets no row then, as their `available` went down when the price was held; the lender's gets `+price`. `payLender` does the same payment on its own, to make up a payment that was missed.
- The deposit is negotiated before acceptance, and only the deposit: the rental price is fixed. The item value is shown as the suggested deposit. An offer or a counteroffer is a whole amount from 1 to 99,999 PP (the same cap as a listing price).
    1. On a request without an offer, the lender either sends an offer (the deposit and both exact addresses) or declines.
    2. On the lender's offer, the borrower accepts, declines or sends one counteroffer; a counteroffer the borrower's available balance cannot cover is refused.
    3. On a counteroffer, the lender accepts or declines. There is no further round.
- The rental stays `REQUESTED` during the negotiation. Accepting makes it `ACCEPTED`; the deposit is reserved then, and acceptance fails if the balance is too low. Declining an offer or a counteroffer makes it `DECLINED`.
- An offer or a counteroffer expires after 1 week without an answer, or on the rental's first day (from midnight in Zurich, like every rental date) if that comes sooner, and the rental becomes `DECLINED`. It cannot be accepted after that. A request that has no offer yet on the rental's first day becomes `DECLINED` then too, since the lender can no longer make one; `expireOffers` declines it in its hourly run, with a `SYSTEM` message in the chat. Once `requestRental` reserves the rental price, every decline, this one included, must release it.
- The wallet is stored in Firestore (see "Firestore schema"). Accepting an offer (`respondToOffer`, `ACCEPT`) holds the deposit in the borrower's wallet, in the same transaction, and fails with an insufficient funds error (`failed-precondition`) if the borrower's `available` balance is too low, leaving the rental `REQUESTED`. The rental price is not reserved yet (`heldForRentals` stays 0). The pickup scan (`confirmHandover`) pays the lender, through the same steps as `payLender`.
- The held deposit is settled when a rental closes, by a shared step in `functions/src/wallet.ts` (`readDepositSettlement`, `writeDepositSettlement`) that runs inside the closing function's transaction; there is no callable of its own. For now an agreed split in direct settlement (`acceptSplit`) calls it, and cancelling an accepted rental (`cancelRental`) gives the deposit back through it, with `release`; the "Item is fine" function (#424) will call it for a clean return. The amount settled is the rental's `deposit` less its `lateFees`, each read as 0 when missing or invalid and never below 0: the late-fee job takes the fees from the held deposit and pays the lender itself, so settlement does not pay them again. The borrower's `heldAsDeposits` goes down by that amount. A clean return gives all of it to the borrower's `available`, with a `DEPOSIT_RELEASED` row `deposit_released_<rentalId>`. A split gives the lender's share to the lender's `available` and the rest to the borrower's, with a `DEPOSIT_SPLIT` row `deposit_split_<rentalId>` for each side that receives PolyPoints (none for a share of 0, as a history amount is never 0), the borrower's share rounded down as in "Disputes". It is idempotent without a field of its own: the deposit counts as settled once the borrower's released or split row, or the lender's split row, exists. If the borrower has no `deposit_held_<rentalId>` row (a rental from before deposits were held), no money moves. If the borrower's `heldAsDeposits` is below the amount, it fails with `internal` and writes nothing.

**Listings and booking**
- A title of at most 80 characters and a description of at most 2,000. A listing already longer, written before the limit, stays readable, but the rules refuse any edit of it until it fits.
- Price per day. The lender sets an availability window; the borrower picks dates inside it with a date picker.
- 3 to 10 listing photos, taken with the in-app camera only (no gallery).
- Pickup and drop-off addresses are typed as text; a Cloud Function geocodes them when the listing is saved. Only the area is public (its name and a point rounded to about 1 km); the exact address is shown after acceptance.
- A 1-day buffer comes before and after every booking. Booked days and buffer days are not selectable.
- Accepting a request auto-declines other requests whose dates overlap (buffer included).
- Your own listings never appear in Browse. Categories are a hardcoded list: Electronics, Sports & outdoor, Books & course material, Tools & DIY, Kitchen & home, Music, Other.

**Cancelling**
- Either party can cancel until the day before pickup. On the pickup day the rental is locked.
- A request that was never accepted can be withdrawn at any time, even on or after its pickup day.
- If the item is still not back from the previous rental on the pickup day, the rental is auto-cancelled and the borrower gets the reserved price and deposit back.

**Handover**
- QR scan at pickup and at return. The person receiving the item scans: at pickup the lender shows the code and the borrower scans; at return the borrower shows and the lender scans.
- The QR holds a secret code made for this rental and phase, so a correct scan proves the two phones met (the rental id alone would let the borrower confirm from home). The person showing it reads the code; the person scanning reads only its fingerprint (SHA-256, 64 lowercase hex characters), which checks a scan on the phone without revealing the code. A wrong code is refused on the phone and never sent. The server checks the code again before moving the rental on. The code must be at least 128 random bits from a secure generator (e.g. `crypto.randomBytes(32).toString("base64url")`): the person scanning can read the fingerprint before the meeting, and a short code (such as 6 digits) could be found by trying every code against it, then confirmed from home. Both are read with a plain `get()`, so offline the phone uses the copy Firestore kept from the last read. The fingerprint is a field of the rental, which My rentals and Rental detail already keep on the phone; the code to show is read only when Handover opens, so a phone that never opened Handover online cannot show it offline. Later, a background job (WorkManager, with the local upload queue) will read the code whenever the phone is online. Until scans can wait in the upload queue, the scan needs a connection, so the phone checks a code offline only once that queue exists.
- The code shows, and the scan is enabled, only on the pickup day and once the person has 3 photos. Until the local upload queue exists, sending a scan needs a connection.
- At each handover, each person takes their own 3 to 20 condition photos; the scan is disabled until they have 3. Photos can also be taken mid-rental from Rental detail.
- Offline: photos and QR scans go into the local upload queue and sync later. The server trusts the app's order (a scan is accepted even if its photos are still uploading).
- After the return scan, the lender chooses "Item is fine" (full deposit released) or "Flag damage" (opens a dispute).

**Late returns**
- 3-day grace period after the deadline, with reminders. Each late day costs the price per day + 2 PP, taken from the deposit and paid to the lender. Fees stop when the deposit is used up. After 3 days the item is Lost and the rest of the deposit goes to the lender.

**Disputes**
1. Direct settlement: parties propose splits in percent; accept or counter. Auto-escalates after 30 days without agreement; either party can escalate sooner. It is the only stage that escalates, by hand or on its own.
2. LLM proposal: a Cloud Function sends the item and both parties' pickup and return photos to Gemini and gets a split + reasoning. Both parties accept or reject. If it fails, either party can try again (up to 3 attempts) or reject.
3. Court: once the dispute reaches court, because either party rejected the LLM proposal, the deposit is frozen. Either party uploads the court ruling PDF; Gemini pre-fills the split; an admin reviews it on the Admin court ruling screen and applies or rejects it.
- A split is applied in whole PolyPoints: the borrower's share is rounded down and the lender gets the rest, so the shares always add up to the deposit (50% of 33 PP gives 16 PP to the borrower, 17 PP to the lender). The Cloud Functions that apply a split must round the same way as the app.
- The chat stays open during a dispute. Reviews (1–5 stars, no text for now) are prompted when a rental closes, however it closed, or once it is lost.
- An agreement settles the dispute, closes the rental and, in the same transaction, splits the held deposit between the two wallets (see "Money"): the lender's share and the borrower's share are those of the deposit left after the late fees, and the chat message shows those amounts, or only "Dispute settled · {lenderPercent}% to the lender" when nothing moved although there was a deposit to settle (no `deposit_held_<rentalId>` row), since it must not claim amounts that were never paid.
- For now no model is configured: `draftLlmProposal` marks every LLM proposal `FAILED` at once, until the Gemini client exists (#452), so the parties can only try again (up to 3 attempts) or reject it, which moves the dispute to `COURT`, and nothing lets them accept a proposal yet (#432). Nothing happens in court yet: the rental stays `DISPUTED` and the deposit stays held.

## Technical choices

Packages: `model/` (data and repositories), `ui/` (screens and their ViewModels), `ui/theme/` (theme). ViewModels depend on repository interfaces and never import Firebase. New Firestore repositories use the shared helpers in `model/firestore/FirestoreHelpers.kt` (reading fields, errors, write timeout, listening to a query, calling a Cloud Function) instead of copying them; Rental, Listing, Profile, Chat, Handover, Wallet and Dispute use them.

Cloud Functions live in `functions/`, a separate TypeScript project (Node 22, `firebase-functions` v2, Jest). `src/index.ts` exports every function and sets the region, `europe-west1`, next to the Firestore database (`eur3`). In `functions/`: `npm ci` installs, `npm run lint` type-checks, `firebase emulators:exec --only firestore "npm test"` runs the tests on the Firestore emulator (external APIs are faked), and `firebase deploy --only functions` deploys (needs the Blaze plan). API keys live in Secret Manager. CI runs the install, lint, build and test steps in its own job. Rental detail opens Start Pickup and Start Return, the chat Start Pickup, and Handover its pickup and return photos, from `serverToday`'s `now`, through `ServerClock` (see "Repositories: one per feature"), which works the day out offline from the last answer; the app does not use `today` yet.

**`reserveDeposit({rentalId})`** holds the deposit of an accepted rental. Accepting an offer already holds it (see below), so this is a safe repeat: it finds the row and succeeds without a second charge. The caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower or its lender, and the rental must be `ACCEPTED`, unless the deposit is already held. The checks run in this order: the rental exists, the caller is a participant, the borrower is valid, the row already exists (the call succeeds, even if the rental has moved on, e.g. to `ACTIVE`), the status is `ACCEPTED`, the deposit is valid, the balance covers it. The amount (`deposit`), the people (`borrowerId`, `ownerId`) and the item title (`listingTitle`) come from the rental, never from the request. In one Firestore transaction on the borrower's wallet, `available -= deposit`, `heldAsDeposits += deposit`, and one `DEPOSIT_HELD` row is added to the borrower's history with the id `deposit_held_<rentalId>`, the amount `-deposit`, the item title and a server timestamp. If `available` is below the deposit, the call fails with an insufficient funds error (`failed-precondition`) and writes nothing. It is idempotent: the row is looked for in the same transaction, so a second call for the same rental changes nothing and succeeds. It writes only the borrower's wallet, even when the lender calls it, and returns nothing, so the lender learns only whether the borrower's balance covers the deposit (the insufficient funds error), never the balance itself. The read and write steps on a wallet are in `functions/src/wallet.ts`, for the other functions that move PolyPoints: `readWallet`, `requireFunds` (the funds check, called after the other checks) and `writeDepositHold`, and, when a rental closes, `depositToSettle`, `readDepositSettlement` and `writeDepositSettlement`. `respondToOffer` with `ACCEPT` uses the same steps inside its own transaction: the borrower's wallet is read with the other reads, and the check, run before any write, throws the same insufficient funds error with nothing written (the rental stays `REQUESTED`, the offer stays, `bookedRanges` is untouched and no overlapping request is declined). The borrower pays whoever accepts, and the amount is the offer's: after a counteroffer, the counter amount. It holds only the deposit, `DEPOSIT_HELD` row `deposit_held_<rentalId>` included; it does not reserve the rental price, call `payLender`, or release or split the deposit (`acceptSplit` does, see "Money").

**`payLender({rentalId})`** pays the lender the rental price once the item has been picked up. The caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower or its lender, and the rental must have been picked up (status `ACTIVE` or any later one: `RETURNED`, `OVERDUE`, `DISPUTED`, `FROZEN`, `LOST`, `CLOSED`), unless the payment was already made; a payment missed while the rental was `ACTIVE` (app killed, offline scans synced together) can still be made up afterwards. The checks run in this order: the rental exists, the caller is a participant, the borrower and the lender are valid and different, the payment already exists (the call succeeds, whatever the status is by now), the status is one of those above, the price is valid, the borrower's balance covers it. The amount (`totalPrice`), the people (`borrowerId`, `ownerId`) and the item title (`listingTitle`) come from the rental, never from the request. In one Firestore transaction, the borrower's `heldForRentals -= totalPrice` (the price held when the request was sent) and the lender's `available += totalPrice` (their wallet is created if missing), and one `RENTAL_PAYMENT` row with the id `rental_payment_<rentalId>`, `+totalPrice`, the item title and a server timestamp, is added to the lender's history. The borrower's history gets no row: their `available` does not change. Until the price is held when a request is sent (#357), a price that `heldForRentals` does not cover is taken from the borrower's `available` instead, as before, with a `RENTAL_PAYMENT` row `-totalPrice` in the borrower's history too; remove this once the price is held. If neither covers it, the call fails with an insufficient funds error (`failed-precondition`) and writes nothing. It is idempotent: the lender's row is looked for in the same transaction, so a second call changes nothing and succeeds (payments made before this rule also wrote a row for the borrower, and still count). It returns nothing, so the lender learns only whether the price is covered, never the borrower's balances. The pickup scan uses the same steps (`functions/src/payLender.ts`: `requireParties`, `isLenderPaid`, `readLenderPayment`, `writeLenderPayment`) inside its own transaction.

**`confirmHandover({rentalId, phase, code})`** confirms a handover scanned in the app, with `phase` `PICKUP` or `RETURN`. The person receiving the item scans, so the caller must be signed in with a verified `@epfl.ch` account and be the rental's borrower at pickup, its lender at return. `code` is the text read from the other person's QR code, compared exactly, untrimmed, in constant time. The server trusts the app's order: the photos are not checked.
- **Pickup.** The checks run in this order: the rental exists (`not-found`), the caller is its borrower (`permission-denied`), then, if the rental was already picked up (`ACTIVE` or any later status), the call succeeds and changes nothing, so a scan sent twice is harmless; otherwise the rental must be `ACCEPTED` (else `failed-precondition` with `details.reason` `RENTAL_CHANGED`), today in Zurich (the server's clock) must be its `startDate` (else `failed-precondition` with no reason), the code must be the one in `handoverCodes/PICKUP` (else `failed-precondition` with `details.reason` `WRONG_CODE`), and the borrower's balance must cover the price (as for `payLender`). In one transaction, the rental becomes `ACTIVE` with `pickedUpAt`, the lender is paid as by `payLender` (not again if they already were), a `SYSTEM` message "Picked up · rental started" is added, seen by the borrower, and the pickup code and `pickupCodeHash` are deleted. A rental accepted before the return code existed gets it then, in the same transaction.
- **Return.** The checks run in this order: the rental exists (`not-found`), the caller is its lender (`permission-denied`), then, if the rental was already returned (`RETURNED`, `CLOSED`, `DISPUTED` or `FROZEN`), the call succeeds and changes nothing; otherwise the rental must be `ACTIVE` or `OVERDUE` (else `failed-precondition` with `details.reason` `RENTAL_CHANGED`), today in Zurich must be its `endDate` or a later day, as a late item is returned the same way (else `failed-precondition` with no reason), and the code must be the one in `handoverCodes/RETURN` (else `WRONG_CODE`). In one transaction, the rental becomes `RETURNED` with `returnedAt`, a `SYSTEM` message "Returned · waiting for the lender's check" is added, seen by the lender, and the return code and `returnCodeHash` are deleted. No money moves: the deposit stays held until the lender's check.
- **The codes.** Both are made when the offer is accepted (`respondToOffer`, `ACCEPT`, in the same transaction), the return's too, so the borrower's phone can keep a copy before the return: each is 32 random bytes from Node's `randomBytes`, as base64url (43 characters), stored in `rentals/{rentalId}/handoverCodes/{phase}` (`code`), with its SHA-256 in lowercase hex as `pickupCodeHash` or `returnCodeHash` on the rental (`functions/src/handoverCode.ts`). A rental that ends before its return must lose its unused codes in the Function that ends it: cancelling an accepted rental (`cancelRental`) deletes both codes with `pickupCodeHash` and `returnCodeHash`, and the future Function that marks an item lost must delete the return code with `returnCodeHash` (the pickup's is gone since the pickup scan). Rentals already active before the return code existed have none and cannot be returned by a scan; they were test rentals only.

**`cancelRental({rentalId})`** cancels a rental for either participant (see "Cancelling") and returns `{}`. The caller must be signed in with a verified `@epfl.ch` account and be the rental's lender (`ownerId`) or borrower (`borrowerId`). The checks run in this order: the rental exists (`not-found`), the caller is a participant (`permission-denied`), then, if the rental is already `CANCELLED`, the call succeeds and changes nothing, so a cancel sent twice (a retry after a lost answer) is harmless; otherwise the rental must be `REQUESTED` or `ACCEPTED` (else `failed-precondition` with `details.reason` `RENTAL_CHANGED`). A `REQUESTED` rental can be cancelled at any time, even on or after its first day, as it holds no money and blocks no day. An `ACCEPTED` one must have valid dates (else `internal`) and is refused from its first day, midnight in Zurich by the server's clock (`failed-precondition` with `details.reason` `TOO_LATE`); it must then have a `listingId`, a borrower and a lender who are different users, and a valid deposit (else `internal`). In one transaction, the rental becomes `CANCELLED` with no `offer`, its `private/addresses` are deleted, and a `SYSTEM` message "Cancelled" is added, seen by the caller. For an `ACCEPTED` rental, the same transaction also removes its `{start, end}` from the listing's `bookedRanges` (skipped if the listing was deleted), deletes both handover codes (`handoverCodes/PICKUP` and `handoverCodes/RETURN`, both made at acceptance) and both hashes (`pickupCodeHash` and `returnCodeHash`), and gives the deposit back through the shared settlement step (`functions/src/wallet.ts`, `writeDepositSettlement` with `release`), only if it was held, that is if the borrower's `deposit_held_<rentalId>` row exists (otherwise nothing moves): the borrower's `heldAsDeposits -= deposit` and `available += deposit`, with one `DEPOSIT_RELEASED` row of `+deposit`, the item title and a server timestamp, at the id `deposit_released_<rentalId>`, looked for in the same transaction so the deposit is never released twice. A wallet whose `heldAsDeposits` is below the deposit is refused as `internal`, since releasing it would create PolyPoints. The rental price is not released, as it is not reserved yet (#357). The logic is in `functions/src/cancel.ts`.

**`submitReview({rentalId, stars})`** saves a participant's review of the other one once their rental is closed or lost (see "Profile & reviews" in SCREENS.md) and returns `{}`. The request carries only `rentalId` and `stars`; everything else comes from the rental. The checks run in this order: the caller is signed in with a verified `@epfl.ch` account (else `unauthenticated` or `permission-denied`), `stars` is a whole number from 1 to 5 and `rentalId` is given (else `invalid-argument`), the rental exists (`not-found`), the caller is its borrower or its lender (`permission-denied`), the rental has a valid borrower and lender, two different users (else `internal`), the rental is `CLOSED` or `LOST` (else `failed-precondition` with `details.reason` `NOT_CLOSED`), the caller has not reviewed it yet (if they have, the call succeeds and changes nothing, so a review sent twice, such as a retry after a lost answer, is harmless and the first stars stay), the other participant, the reviewee, has a `users/{uid}` document (else `not-found`), and the reviewee's stored rating is valid: with a `reviewCount` above 0, `averageRating` must be a number from 1 to 5 (else `internal`, as the rating is broken). In one transaction, it creates `users/{revieweeId}/reviews/{rentalId}` (see "Firestore schema"), with the author's name (`ownerName` or `borrowerName`) and the item's title (`listingTitle`) copied from the rental, and updates the reviewee's profile: `reviewCount` goes up by 1 and `averageRating` becomes (old average × old count + stars) ÷ (old count + 1), not rounded, a missing field reading as 0. The review is looked for in the same transaction, so of two reviews sent at once only one counts, and both calls succeed. It adds no chat message.

## Firestore schema

Dates without a time are stored as `YYYY-MM-DD` strings, prices as whole PolyPoints. Date-times (`createdAt`, `lastMessageAt`, `lastReadAt`, `sentAt`, `takenAt`) are Firestore Timestamps, set with `FieldValue.serverTimestamp()` (except a condition photo's `takenAt`, set by the phone from `ServerClock`, as the photo may be sent long after it was taken); reads use `ServerTimestampBehavior.ESTIMATE`, because until the server confirms a write a listener otherwise sees these fields as null. When a new field is added to an existing collection, reading must give it a default value: documents written before it do not have it.

Listings:
- `pickupArea` and `dropOffArea` are area names (e.g. "Ecublens"); `pickupPoint` and `dropOffPoint` are GeoPoints. The app creates a listing with empty names and no points; the `geocodeListingAddresses` Cloud Function fills them in. Each time `listings/{listingId}/private/addresses` is written, it geocodes each changed address (in Switzerland only) and stores its area name and its point rounded to a 0.01° grid (about 1.1 × 0.8 km around EPFL). The exact address and point never reach the public listing. A lookup that fails (e.g. the Geocoding API is down or takes more than 10 seconds) is retried for up to a day, and a result is written only if its address has not changed since, so the newest edit wins even if its run finishes first.
- Until an address is geocoded, or when it is blank, not found or its geocoding fails, its name and point are missing, and screens show a placeholder.

Rentals:
- The listing title, both names and the public areas are copied when the rental is created, so My rentals and the chat list need no other read. A missing owner name is stored as `""`; screens show a translated placeholder.
- `participants` is `[ownerId, borrowerId]`; the chat list queries it with `array-contains` only and sorts by `lastMessageAt` in the app, so it needs no composite index.
- My rentals queries `borrowerId` or `ownerId` only and sorts newest first in the app (a user has few rentals), so it needs no index.
- `lastMessageAt` is set to the same server timestamp as `createdAt` when the rental is created: the chat list sorts by it, and leaves out a rental that lacks it.
- `lastReadAt` maps each participant's uid to when they last saw the chat; it is missing until someone does, and reads as empty. The app saves the user's own entry at the server time while the chat is on screen: when it shows its messages, and each time a newer one from someone else arrives. It saves nothing while the chat is hidden (another screen on top, or the app in the background), while it shows no message, or offline, where the server time would only be set on reconnecting and would also cover messages received meanwhile; it saves once the connection is back. Sending a message saves the sender's entry in the same write, and each Cloud Function that adds a `SYSTEM` message saves the entry of the participant whose action it reports (nobody's for a scheduled job such as `expireOffers`), so a user's own messages and actions are never unread. A conversation is unread for a user when it has a last message newer than their entry, or they have no entry; the chat list then shows a red dot. Rentals created before `lastReadAt` existed show a dot on every conversation with a message until it is opened.
- `pickupAddress` and `returnAddress` stay empty until the rental is accepted; the borrower cannot read the exact addresses before that. The lender's offer stores them in `private/addresses`, and acceptance copies them onto the rental.
- `deposit` is the accepted amount in PolyPoints; missing reads as 0.
- `pickedUpAt` is when the pickup scan was confirmed, a server Timestamp set by `confirmHandover`; it is missing until then.
- `cancelledAt` is when the rental was cancelled, a server Timestamp. Nothing writes it yet (#503); once something does, only Cloud Functions will (`cancelRental`, #429, and later the auto-cancel). Missing reads as null, and Rental detail then shows "Cancelled" with no date.
- `returnedAt` is when the item was given back, a server Timestamp. Only Cloud Functions write it: `confirmHandover` (`RETURN`) sets it at the return scan. Missing reads as null, and Rental detail then shows "Returned" with no date.
- `lateFees` is the total of the late fees taken from the deposit, in PolyPoints. Only Cloud Functions will write it, the scheduled job that charges late fees, once a return is late, so a rental that was never late has no such field, and missing reads as 0. The job takes each fee from the borrower's heldAsDeposits and pays it to the lender, in a transaction that reads the rental, and stops once the rental is CLOSED; deposit settlement only moves what is left.
- `offer` is the offer waiting for an answer: `amount`, `authorId`, `isCounter`, `createdAt`, `expiresAt`, and on a counteroffer `previousAmount`, the lender's offer. It is missing when no offer is waiting, and removed when the negotiation ends. `expireOffers` queries `offer.expiresAt` alone, and requests with no offer on `status` alone with the dates checked in the code, so it needs no composite index, and answering also refuses an expired offer, in case `expireOffers` has not run yet.
- `pickupCodeHash` and `returnCodeHash` are the fingerprints of the handover codes (see "Handover"): the SHA-256 of the code, as 64 lowercase hex characters. The code must be at least 128 random bits, or it could be found from its fingerprint. Written by Cloud Functions only. Missing reads as no code, and the scan stays disabled.
- Each step of the negotiation adds a `SYSTEM` message to the chat, written by the Cloud Functions; the chat's offer card reads `offer`, so there is no new message type.
- **Creating a request.** Only the `requestRental` Cloud Function creates a rental; the security rules refuse every client creation. The app sends the listing's id and the days only. The caller must be signed in with a verified `@epfl.ch` account and must not own the listing; the listing must exist and be `PUBLISHED`; the days must be inside its availability window, the first one after today in Europe/Zurich (a request starting today could get no offer), and must not conflict with `bookedRanges`, buffer day included; all these refusals carry `details.reason` `DATES_UNAVAILABLE`. Sending the same request again (same borrower, listing and days, still `REQUESTED`) returns the first rental, so a retry after a lost answer never creates a second one; a pending request of the same borrower with other days in common is refused with `already-exists`. The listing is read and the rental written in one transaction, so two requests sent at once are checked against the same `bookedRanges` (both go through, since a pending request blocks no day). Every other field comes from the server: the owner and the borrower names from `users/`, the title, the first photo (`""` without one), the price per day and the areas from the listing, `totalPrice` (price per day × days), `participants`, status `REQUESTED`, empty addresses and last message, and `createdAt` and `lastMessageAt` at the same server timestamp. A booked day fails with `failed-precondition` and `details.reason` `DATES_UNAVAILABLE`, a missing listing with `not-found` and an unpublished one with `failed-precondition`; the app reads them to show "These dates are no longer available" or the listing as not found. No money is reserved yet. Afterwards the participants can change only `lastMessage` (never empty, which would read as no message), `lastMessageAt` (to the server time) and their own entry of `lastReadAt` (to the server time), and an update must change something.

Wallet:
- `WalletRepositoryFirestore` only reads, with snapshot listeners that serve the cache first (and `MetadataChanges.INCLUDE`), so the wallet and the history stay readable offline from the cache, and it never forces a server read. A missing wallet document, or an empty history, that comes from the cache is not emitted: from an empty cache (after a reinstall, or a first launch offline) it cannot be told from a real empty one, so it is emitted only once the server has confirmed it, and until then the balance and the history are unknown (not 0, not empty). The history is not sorted there (`WalletViewModel` sorts it). An invalid uid reads as an empty wallet and history. `recharge` always fails ("not available yet") until a recharge Cloud Function exists. `WalletViewModel` sets `isUnreachable` when the phone has been online for 10 seconds while the wallet or the history is still unknown and there is no error; the wait restarts on `retry()` and each time the phone comes back online. As the phone is online then, `isOffline` and the offline banner are untouched; the screen shows the offline layout with its own texts, and `recharge` is refused like offline. A confirmed snapshot resets it, and a value already known is never replaced.
- Until recharging exists, a user has only the 120 PP they start with (see "Money"); give a test user more by hand: edit `wallets/{uid}` in the Firebase console, or write it with a script against the emulator (Admin SDK or the emulator's REST API with the `Bearer owner` token, which skips the rules). Add a matching `RECHARGE` row in `transactions` if the history should add up to `available`.

Disputes:
- One per rental, at the rental's id. Nothing is copied from the rental: the item, both participants and the deposit are read from it.
- `stage` is `SETTLE`, `LLM_PROPOSAL` or `COURT`. `proposals` lists every split, oldest first, each `{authorId, lenderPercent, createdAt}` with `lenderPercent` a whole number from 0 to 100; `createdAt` is set by the Cloud Function from its own clock, because a server timestamp is not allowed inside a list. `escalatesAt` is when direct settlement escalates by itself: 30 days (`SETTLE_DAYS` in `functions/src/disputeRules.ts`) after the dispute opens, set by `openDispute`, and not changed afterwards. A dispute without it never escalates by itself, in the Cloud Functions and in the app, which then shows no days left. `escalatedBy` is the uid of the participant who escalated, or null when it escalated by itself or has not escalated; in `COURT`, it is the participant who rejected the LLM proposal. `agreedAt` is set when a split is accepted, and null before; it, not `stage`, tells whether the dispute is settled (an agreement leaves `stage` at `SETTLE`).
- `openDispute({rentalId})` opens the dispute when the lender taps "Flag damage" on Handover, and returns `{}`. The caller must be signed in with a verified `@epfl.ch` account and be the rental's lender. The checks run in this order, in one transaction: the rental exists (`not-found`), the caller is its lender (`permission-denied`, the borrower included), then, if `disputes/{rentalId}` already exists, the call succeeds and changes nothing, whatever the rental's status by now (`DISPUTED`, `FROZEN`, `CLOSED` by the dispute…), so an answer lost on the way is harmless; otherwise the rental must be `RETURNED` (else `failed-precondition` with `details.reason` `RENTAL_CHANGED`, e.g. when "Item is fine" was sent first; the app shows it as a plain failure). In the same transaction it creates `disputes/{rentalId}` as `{stage: SETTLE, proposals: [], escalatesAt: now + 30 days, escalatedBy: null, agreedAt: null}`, with no `llmProposal`, and makes the rental `DISPUTED` with a `SYSTEM` message "Damage flagged · dispute opened", seen by the lender. No wallet is written: the deposit stays held, a deposit of 0 included.
- `proposeSplit({rentalId, lenderPercent})` adds a split, refused if it is the latest one or if the dispute already holds 500 (far more than a real negotiation; it keeps a script or a bug from growing the document towards Firestore's 1 MiB limit). `acceptSplit({rentalId, lenderPercent})` accepts the latest split, which must be the other participant's and give the lender `lenderPercent`; it sets `agreedAt`, closes the rental and settles the held deposit (see "Money"). `escalateDispute({rentalId})` moves the dispute to `LLM_PROPOSAL`. The hourly `escalateDisputes` does the same, with `escalatedBy` null, for each dispute still in `SETTLE` and not settled once `escalatesAt` has passed; it queries `escalatesAt` alone, so it needs no composite index. Like the callables, it leaves a dispute whose rental is missing or not `DISPUTED` as it is, and logs it as a failure at each run. The three callables (`proposeSplit`, `acceptSplit`, `escalateDispute`) refuse a settled dispute, one no longer in `SETTLE`, and one whose rental is not `DISPUTED` (only `openDispute` sets that status, so an agreement never overwrites another one). Once `escalatesAt` has passed, even before the sweep runs, they escalate the dispute instead, as the sweep would (`escalatedBy` null), and fail with `STAGE_CHANGED`. A request that lost a race fails with `failed-precondition` and `details.reason`: `PROPOSAL_CHANGED` (the latest split is not the one accepted) or `STAGE_CHANGED` (the dispute was settled or left `SETTLE`); the app reads the reason, never the message.
- `llmProposal` is the LLM proposal: `{status, attempt, lenderPercent, reasoning, model, photoIds, createdAt}`. Escalating, by hand or by itself, creates it as `{status: PENDING, attempt: 1}` in the same write; it is missing in `SETTLE` and on disputes escalated before it existed, which can only be test disputes made by hand, as no Function opened a dispute before `openDispute`; rejecting and retrying refuse them, with no reason. `status` is `PENDING` (waiting for the model), `READY` or `FAILED`. `lenderPercent` (a whole number from 0 to 100), `reasoning` (English, at most 2,000 characters), `model` (the model's name) and `photoIds` (the condition photos it was sent) are set only when `READY`; `createdAt` is the server time it became `READY` or `FAILED`.
- The trigger `draftLlmProposal` runs on each update of `disputes/{rentalId}` and acts only when the update starts a new `attempt` of a `PENDING` proposal, so its own writes never start it again. Through the `SplitAdvisor` interface (`functions/src/splitAdvisor.ts`, see docs/adr/0001), it sends the model the item's title, description and value, the deposit, the rental's dates, and both parties' pickup and return photos (at most 20 per party per phase, oldest first, given by their Storage path, never their `url`), naming the missing ones; never the split proposals nor the chat (docs/adr/0002). The rule it gives the model: the lender's share is the cost of new damage as a percentage of the deposit, normal wear is not damage, and missing return evidence counts against the borrower. It writes `READY`, or `FAILED` when no model is configured, the model refuses for good or its answer breaks these rules; a failure that may pass (the model is down or slow) is retried for up to a day, then `FAILED`. The result is written only if the dispute is still in `LLM_PROPOSAL`, not settled, `PENDING` on the same attempt and its rental `DISPUTED`, so overlapping runs keep the first answer. Each result adds a `SYSTEM` message to the chat, from nobody.
- The parties answer the LLM proposal through two callables (`functions/src/llmProposalAnswers.ts`). `rejectLlmProposal({rentalId})` rejects a `READY` proposal or a `FAILED` one (the way out once no attempt is left): the dispute moves to `COURT` with the caller as `escalatedBy`; the rental stays `DISPUTED` and the deposit stays held. `retryLlmProposal({rentalId})` sets a `FAILED` proposal to `{status: PENDING, attempt: n + 1}` while `attempt` is below 3, which starts `draftLlmProposal` again. Both refuse a settled dispute, one not in `LLM_PROPOSAL` (`STAGE_CHANGED`) and one whose rental is not `DISPUTED`; rejecting is refused on a `PENDING` proposal, and retrying on a `PENDING` or `READY` one, with `details.reason` `LLM_PROPOSAL_CHANGED`: another attempt started since the user saw the failure, so two retries sent at once, or a retry sent again after its answer was lost, start one attempt and the app follows the dispute instead of showing an error.
- Opening the dispute, an agreement, an escalation and a rejection of the LLM proposal add a `SYSTEM` message to the rental's chat; a proposal and a retry add none.

Listing photos uploaded by the app go to Cloud Storage under `listings/{listingId}/`, as `0.jpg` to `9.jpg`, each tagged with the uid of the user who uploaded it (custom metadata `uploader`), so the Storage rules can check the owner and the uploader. Photos added before this rule live in `listing_images/` and keep working through their download URLs. Condition photos go to `rentals/{rentalId}/photos/{photoId}.jpg`, named after their Firestore document, so `{uid}_PICKUP_{n}.jpg` (see the schema above); photos stored before the slot ids keep their random names. A profile photo goes to `users/{uid}/profile.jpg`, one file per user that each new photo replaces; replacing it gives a new download URL, so the new photo is not hidden by an image cache.

## Security rules

`firestore.rules` and `storage.rules` are listed in `firebase.json`, so the emulators enforce them; `FirestoreRulesTest` and `StorageRulesTest` (in `androidTest/.../rules/`) check them. Every read and write needs a verified `@epfl.ch` account. Beyond the notes in the schema above:
- A listing must pass the same checks as `Listing.canPublish` (a title of at most 80 characters and a description of at most 2,000, neither blank, 3 to 10 photo URLs, all strings, prices from 1 to 99,999 PP, `availableFrom` before `availableTo`, a known category and status). Clients never write `bookedRanges` (Cloud Functions do) and never change `ownerId`. They create `pickupArea` and `dropOffArea` empty, never write `pickupPoint` or `dropOffPoint`, and never change any of the four afterwards (`geocodeListingAddresses` does). A listing cannot be created at an id whose `private/addresses` is left over from a deleted listing.
- A listing is locked while an accepted rental of it ends today or later (#341): its owner can neither update nor delete it, nor write or delete its `private/addresses` (still readable), nor add, replace or delete its photos in Storage. The rules cannot loop over a list, so they read only the last range of `bookedRanges`, which Cloud Functions keep sorted by `start`; lists stored out of order before that are sorted once by `sortBookedRanges` (`functions/src/sortBookedRanges.ts`), run by hand after deploying. They know only UTC, so their "today" is the date at UTC+1: Zurich's in winter, and in summer the lock lasts until 1 a.m. on the day after the last booked day. A listing unlocks once its last booking is over, or once that booking's range leaves `bookedRanges`, which cancelling an accepted rental does (`cancelRental`).
- A rental request must match its listing, which must be `PUBLISHED`: same owner, title, first photo (`""` if the listing has none), price per day and areas, dates inside the availability window, and `totalPrice` equal to the price per day × the number of days.
- Clients never write a rental's `deposit`, `offer`, `pickupAddress` or `returnAddress`, and have no access to `rentals/{rentalId}/private/addresses`.
- Wallets: a user reads only their own `wallets/{uid}` and its `transactions`; nobody writes them from the app, the owner included (`allow write: if false`). Cloud Functions write them.
- A dispute is read only by the two participants of its rental (`participants`), and never written by a client.
- Reviews (`users/{uid}/reviews/{rentalId}`) have no client access yet: no rule matches `users/{uid}/reviews`, since the rule for `users/{uid}` does not cover its subcollections, so every read and write is refused. Their read rule comes with #354; `submitReview` writes them.
- A handover code (`rentals/{rentalId}/handoverCodes/{phase}`) is read only by the person who shows it: the lender for `PICKUP`, the borrower for `RETURN`; any other phase by nobody. No client writes it, nor the fingerprints on the rental (`pickupCodeHash`, `returnCodeHash`), which the rental's update rule already keeps out of reach.
- Profiles: a user creates and edits only their own, with their own email; `averageRating` and `reviewCount` are left to Cloud Functions.
- Storage: listing photos must be images under 10 MB (the in-app camera takes about 1440 × 1080 JPEGs at quality 80), named `0.jpg` to `9.jpg` and tagged with the uid of the user writing them. They are uploaded before the listing document exists, so a folder whose listing does not exist yet is open to any verified user; once it exists, only the owner may change it. A photo can be replaced or deleted only by the user who uploaded it, even once its listing is deleted; photos uploaded before the tag existed have none, so only an admin can change or delete them. These rules read Firestore, so the first deploy asks to let Storage read Firestore.
- Storage: a profile photo can be read by any verified user and changed or deleted only by its user; it must be an image under 5 MB, and no other file is allowed under `users/`. The in-app camera takes photos at 1440 × 1080 with JPEG quality 80, a few hundred KB, well under this limit.
- Storage: condition photos are read and added only by the rental's two participants, pickup photos while the rental is Accepted and return photos while it is Active or Overdue, each also up to a day after its scan (Storage cannot see `takenAt`, which the Firestore rules check), as images under 10 MB; they are never replaced or deleted. The file name must be the signed-in user's own slot of that phase, `{uid}_{phase}_{0..19}.jpg`, so a person adds at most 20 per phase: a slot is written once because nobody replaces a photo.
- Condition photo cap (#428): Firestore rules cannot count documents, so the cap is part of the id. A condition photo's id must be the user's own slot of its phase, `{uid}_{phase}_{0..19}` (Firestore) and the file `{uid}_{phase}_{0..19}.jpg` (Storage), on top of the checks above. Photos with other ids, such as the random ones stored before slot ids or sent by old app versions, are refused when added and are not counted. The rules refuse the random ids that old app versions send, so deploy them only after the app update is out. A slot whose file exists in Storage without a document (an upload that finished but whose document was never written) is finished by the upload queue's job, which writes the document for the file already there if it is its own (tagged with its `takenAt`); a file left by another photo is never reused.
- Profile photo URL (#428): a profile's `photoUrl` must be `""` or the download URL of the user's own `users/{uid}/profile.jpg` in this project's bucket (`https://firebasestorage.googleapis.com/v0/b/<bucket>/o/users%2F<uid>%2Fprofile.jpg?alt=media&token=<token>`). It is checked when the profile is created, and when it is updated only if `photoUrl` changes, so an old stored value does not block a name change. The bucket name is written in `firestore.rules`, since the rules cannot read it. The same URL on the Storage emulator's hosts (`http://10.0.2.2:9199`, `http://localhost:9199`, `http://127.0.0.1:9199`, any one-segment bucket) is also accepted, so that the emulator tests can use the URL of a real upload; it is accepted in production too.
- Not enforced yet: the pickup and return days of condition photos (checked in the app); a condition photo's `url` pointing at its own file in Storage (the rules only require a string, so a modified client could point it at any image); locking a listing while a rental of it is still active or overdue after its last day (a late return), since the lock reads only `bookedRanges` (see AGENTS.md); photo URLs pointing at this listing's Storage folder; new photos in folders with no listing (any verified user can still add up to 10 under a made-up or deleted id); a limit on how many requests one borrower sends for a listing (`requestRental` only refuses a second pending request of the same borrower with days in common); keeping drafts private: any verified user can read every listing, so someone else's profile downloads and caches their drafts and only leaves them out on the phone (#308).
